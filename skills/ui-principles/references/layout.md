# 화면 배치: 정하는 방법과 다시 짜야 할 때

새 화면의 배치를 정할 때, 기존 화면에 컨트롤을 더할 때, 화면을 재설계할 때 읽는다.

배치는 기능이 쌓이면서 나빠진다. 기능 하나를 더할 때 가장 쉬운 방법은 빈자리에 컨트롤을 놓는 것이다. 옵션이 생기면 체크박스를 기존 줄 끝에 붙이고, 입력이 하나 더 필요하면 모달을 띄운다. 한 번은 괜찮지만 다섯 번 되풀이하면 화면은 코드의 옵션 목록을 그대로 늘어놓은 모양이 된다. 각 변경은 동작했으므로 아무도 배치를 다시 보지 않는다.

이 문서의 근거는 재설계 사례 한 건과 처음부터 배치를 잡고 시작한 사례 한 건이다. 수치는 기준선이지 법칙이 아니다.

## 배치를 정하는 순서

1. **사용자가 하는 일을 순서대로 적는다.** 구현의 모듈이 아니라 사용자의 동작이다. 예: 내용을 넣는다 → 조건을 맞춘다 → 실행한다 → 결과를 확인한다 → 가져간다.
2. **화면에 놓을 컨트롤을 모두 적고 빈도로 나눈다.**
   - 매번: 작업할 때마다 쓴다(주 입력, 실행, 결과 복사).
   - 가끔: 몇 번에 한 번 바꾼다(모드 전환, 폭, 샘플 불러오기).
   - 드물게: 한 번 정하면 거의 그대로다(세부 옵션, 테마).
3. **매번 쓰는 것만 항상 보이는 자리에 둔다.** 가끔 쓰는 것은 작은 보조 컨트롤로, 드물게 쓰는 것은 접거나 메뉴 안으로 보낸다.
4. **주 동작 하나를 정한다.** 이 화면에서 사용자가 하러 온 일이다. 강조색으로 채운 단추는 이것 하나다.
5. **순서를 방향으로 옮긴다.** 일의 순서가 읽는 방향(왼쪽에서 오른쪽, 위에서 아래)과 같아야 한다. 입력은 왼쪽·위, 결과는 오른쪽·아래.
6. **컨트롤을 그것이 다루는 대상 옆에 둔다.** 입력을 바꾸는 것은 입력 영역에, 결과를 가져가는 것은 결과 영역에, 앱 전체에 걸친 것(테마, 이력, 도움말)만 상단 바에 둔다.
7. **좁은 화면에서 무엇이 남는지 정한다.** 좌우를 위아래로 쌓았을 때의 순서, 숨길 것, 숨긴 것에 닿는 다른 경로.

## 어디에 담을지 고르기

| 담을 것 | 담는 곳 | 이유 |
|---|---|---|
| 주 작업의 입력(둘 이상이면 각각) | 같은 영역의 탭 | 주 입력은 늘 보이는 자리에 있어야 한다. 모달에 넣으면 열 때마다 맥락이 끊긴다 |
| 같은 결과의 다른 보기(미리보기, 코드) | 결과 영역의 탭 | |
| 작업을 보면서 쓰는 부가 기능(이력, 참고 자료) | 서랍 | 작업 화면이 남아 있어야 한다 |
| 드물게 바꾸는 설정 묶음 | 접이식 묶음. 접힌 상태에서 켜진 값을 요약으로 보인다 | 평소에는 자리를 차지하지 않고, 지금 값은 알 수 있어야 한다 |
| 둘셋 중 하나 고르기 | 붙은 단추 묶음 | 지금 값과 선택지가 함께 보인다 |
| 넷 이상 중 하나 고르기 | 드롭다운 | |
| 켜고 끄는 설정 | 스위치 | |
| 잠깐 끼어드는 확인, 짧은 입력 하나 | 모달 | 끝나면 사라져도 되는 것만 |
| 한 번 보고 닫는 도움말(단축키 표) | 모달 | |
| 현재 상태(크기, 건수, 경고 수) | 영역 아래의 상태 줄 | 결과와 붙어 있어야 한다 |

모달은 구현하기 쉽다. 기존 화면을 건드리지 않고 독립된 조각으로 만들 수 있기 때문이다. 그래서 필요 이상으로 쓰이게 된다. 모달을 고르기 전에 위 표의 다른 줄에 해당하지 않는지 먼저 본다.

## 구획의 틀

도구형 앱에서 반복해서 쓰는 틀이다.

- **상단 바**: 얇게(44px 안팎). 왼쪽에 이름, 오른쪽에 전역 동작. 작업의 컨트롤을 두지 않는다.
- **작업 영역**: 입력과 결과를 나란히 둔다. 사이에 크기를 조절하는 분할선을 둔다.
- **영역 하나의 안쪽**: 머리 줄(왼쪽에 탭, 오른쪽에 그 영역의 주 동작) → 접이식 옵션 → 내용 → 아래 줄(보조 동작이나 상태).
- **사이드바**(목록·트리가 있는 앱): 폭 260~300px. 위에 걸러내기, 가운데 목록, 아래에 드물게 쓰는 진입점(휴지통).
- **서랍**: 오른쪽에서 나온다. 여는 단추는 상단 바에 둔다.

영역은 면의 단계와 1px 선으로 나눈다. 테두리를 겹겹이 두르지 않는다.

## 다시 짜야 한다는 신호

하나라도 해당하면 컨트롤을 더 놓기 전에 배치를 본다. 둘 이상이면 재배치를 제안한다.

- 한 줄에 종류가 다른 컨트롤이 다섯 개를 넘는다.
- 같은 층에 강조색으로 채운 단추가 둘 이상이다. 또는 주 동작이 다른 단추와 구분되지 않는다.
- 주 작업의 입력이 모달 안에 있다.
- 체크박스가 코드의 옵션 순서대로 늘어서 있다. 묶음도 순서의 이유도 없다.
- 컨트롤이 그것이 다루는 대상과 떨어져 있다(입력 옵션이 상단 바에 있음).
- 상단 바에 작업의 컨트롤과 전역 동작이 섞여 있다.
- 같은 종류의 정보가 화면 여러 곳에 흩어져 있다(탭마다 다른 빈 상태, 여기저기의 배지).
- 매번 쓰는 동작이 두 번 이상 눌러야 닿는 곳에 있다. 또는 드물게 쓰는 것이 가장 좋은 자리를 차지한다.
- 좁은 화면에서 한 줄이 두세 줄로 꺾인다.
- 사용자가 배치를 설명할 때 "어디 있더라"가 나온다.

## 기능을 더할 때

컨트롤을 놓기 전에 세 가지를 본다.

1. 이 컨트롤은 매번·가끔·드물게 중 어디인가. 그 빈도에 맞는 자리가 지금 배치에 있는가.
2. 놓으려는 줄에 이미 몇 개가 있는가. 놓고 나면 위 신호에 걸리는가.
3. 같은 일을 하는 컨트롤이 이미 있는가. 있으면 합친다.

신호에 걸리면 빈자리에 붙이지 않는다. 요청받은 기능은 구현하되, 사용자에게 "이 기능을 넣으면 이 줄의 컨트롤이 여섯 개가 됩니다. 옵션을 접이식 묶음으로 옮기는 재배치를 권합니다"처럼 무엇이 걸리는지와 어떻게 바꾸면 되는지를 알린다. 재배치는 요청 범위를 넘는 변경이므로 승인을 받고 한다. 알리지 않고 넘어가는 것과 묻지 않고 뒤집는 것 둘 다 하지 않는다.

## 재설계하는 순서

1. **지금 화면의 컨트롤을 모두 적는다.** 숨어 있는 것(모달 안, 메뉴 안, 단축키만 있는 것)도 적는다. 재설계에서 기능이 빠지는 일은 여기서 막는다.
2. 위 "배치를 정하는 순서"를 처음부터 한다. 기존 배치에서 출발하지 않는다.
3. **옮긴 것의 표를 만든다.** 컨트롤마다 이전 위치와 새 위치, 없앤 것은 이유와 대체 경로를 적는다. 사용자에게 이 표로 승인을 받는다.
4. 구조를 먼저 바꾸고 모양은 그다음에 다듬는다. 색·그림자 손질부터 하면 배치 문제가 가려진다.
5. 저장된 설정 값이 새 배치에서도 읽히는지 확인한다. 키를 바꿨으면 옮겨 준다. 기본값을 바꿨으면 알린다.
6. 테스트가 의존하는 식별자(`id`, `data-*`)를 유지하거나 테스트를 함께 고친다.
7. 바꾼 뒤 [SKILL.md](../SKILL.md) 의 마치기 전 점검을 한다. 재배치는 포커스 순서와 좁은 화면 배치를 바꾸므로 그 둘을 특히 본다.

## 재설계 사례

HTML 메일용 CSS 인라이너의 화면을 다시 짠 경우다.

| | 이전 | 이후 |
|---|---|---|
| 상단 | 메뉴 바에 이력, CSS 입력, CSS 가져오기, 템플릿, 내장 CSS 체크가 나란히 | 얇은 바에 이름과 전역 동작(이력, 단축키, 테마)만 |
| 두 번째 입력(CSS) | 모달 | 입력 영역의 탭(HTML / CSS) |
| 옵션 | 입력 영역 머리 한 줄에 체크박스 다섯 개, 폭 입력, 모드 토글, 실행 단추 | 머리 줄에는 모드(붙은 단추 묶음)·폭·실행만. 나머지 스위치는 접이식 묶음으로 가고 접힌 상태에서 켜진 것을 칩으로 요약 |
| 주 동작 | 다른 컨트롤과 한 줄에 섞여 있음 | 입력 영역 머리 오른쪽 끝의 유일한 채움 단추 |
| 보조 동작 | 상단 메뉴 | 입력 영역 아래 줄(파일 열기, 샘플, 비우기) |
| 이력 | 모달 | 오른쪽 서랍 |
| 결과 | 탭마다 다른 빈 상태 | 결과 영역 공통의 빈 상태 하나, 머리 줄에 복사·내려받기, 아래 상태 줄에 크기·통계·경고 |

바뀐 것은 세 가지다. 컨트롤을 일의 순서대로 놓았고, 빈도에 따라 드러내는 정도를 나눴고, 주 입력을 모달에서 꺼냈다. 색과 모양의 변화는 그 뒤에 따라온 것이다.

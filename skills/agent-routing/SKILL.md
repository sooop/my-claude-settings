### 서브 에이전트 모델·effort 선택

워크플로우(`Workflow`)와 서브 에이전트(`Agent`)를 띄울 때는 **작업의 성격에 모델과 effort를 함께 맞춘다.** 기본값은 sonnet(medium)이며, 아래 기준으로 haiku까지 내리거나 opus로 올린다. 모델을 명시하지 않으면 세션 모델(주로 opus)을 그대로 상속하므로, **단계마다 `model`을 의식적으로 지정한다.**

**올리는 순서: effort → 모델.** 더 어려운 일이면 먼저 같은 모델의 effort를 올리고(sonnet medium → high), 그래도 부족할 때만 모델을 올린다. Sonnet 5.5·Opus 5.5 도입으로 sonnet이 소화하는 추론 범위가 넓어졌다. 예전 기준의 "opus 예외"(3항 논리·5단계 이상 추론 사슬·단일 원인 추적)는 **sonnet medium으로 시작**하고, 아래 "high를 올리는 조건"에 해당할 때만 high로 올린다.

**haiku — 판단이 섞이지 않은 수집·추출**
파일 목록화, 심볼·정의 위치 찾기, 정해진 형식으로 인용 모으기, 로케일 키 대조, 대량 항목의 기계적 분류. "무엇이 어디 있는가"에 답하는 일.

**sonnet — 기본값 (범위 확대, medium으로 시작)**
코드를 읽고 구조를 파악하는 일, 규칙 문서와 대조하는 체크리스트 매칭, 호출 경로 추적과 열거, 대부분의 구현·검토. 여기에 **이전에 opus 몫이던 아래 일도 포함한다 — medium으로 시작한다.**
- 의미 판단: SQL 3항 논리(`NULL <> ''`는 UNKNOWN), 타입 좁히기, 순서 의존 분석
- 추론 사슬: SP 중첩 CASE → API → 폼 매핑 → 저장 요청 → 서버 조건처럼 10단계·5계층까지(실측에서 medium이 정답)
- 단일 근본 원인 추적: 3만 줄·200파일 범위도 `rg` 로 좁혀 medium·high 모두 정답
- High 이하 지적의 검증·반증

**high를 올리는 조건 (sonnet medium → high)** — 아래 중 하나일 때만. 점수가 아니라 비용을 쓰는 결정이므로 근거를 남긴다.
- 같은 입력에서 medium 결과가 서로 엇갈렸다.
- 오판 비용이 크다: 검증·반증 단계의 High 이상 지적, 되돌릴 수 없는 변경의 근거.
- 결론의 근거를 실행으로 확인하는 일(패치 적용본을 돌려 보기 등)이 핵심이다 — 실측에서 이 엄밀성은 `verifier`(high)가 더 직접적이었다.

**opus — 좁은 예외**
단순 열거·추적·체크리스트 매칭·단일 원인 추적에는 쓰지 않는다. **지금까지 sonnet이 틀리고 opus가 맞은 사례는 관찰되지 않았다**. 아래에 해당할 때만 쓴다.
1. **sonnet(high)의 결과가 서로 엇갈려 판정이 필요한 경우.**
2. **오판 비용이 큰 Critical 건의 재검증** — 보안 경계, 동시성 정합성, 되돌릴 수 없는 데이터 변경처럼 틀리면 결론 전체와 후속 작업이 무너지는 건.
3. **정답 외의 부수 발견이 필요한 심화 분석** — 영향 범위, 설계 의문, 전제 조건(`NOCOUNT` 등)까지 덧붙이는 경향이 실측에서 반복됐다. 이것은 정확도가 아니라 보고의 폭이므로, 필요할 때만 사고 폭을 사러 쓴다. 시간이 약 2배 든다.

상향 조건은 추정이 아니라 관찰이다. 새 유형이 의심되면 sonnet(high)과 opus에 같은 입력을 돌려 결론이 갈리는지 보고, 갈릴 때만 그 유형을 opus 목록에 올린다. 원인이 둘이거나 증상이 엉뚱한 곳을 가리키는 문제는 아직 시험하지 않았다 — 이 유형은 미검증이다.

**심각도 기반 배분**
검증·반증 단계처럼 항목마다 오판 비용이 다른 경우, 항목의 심각도로 모델과 effort를 가른다. 심각한 지적을 잘못 기각하면 결함이 그대로 남으므로 그쪽에만 비용을 더 쓴다.
```js
const opts = f.severity === 'Critical' ? { model: 'opus', effort: 'high' }
           : f.severity === 'High'     ? { model: 'sonnet', effort: 'high' }
           :                             { model: 'sonnet', effort: 'medium' }
```

**effort 기준**
모델별 기본값: opus·fable·opusplan은 `high`, sonnet은 `medium`. 기본값에서 벗어나는 지정만 의미가 있다.
`low` 수집·추출·기계적 분류(주로 haiku) / `medium` 구현·읽기·체크리스트 매칭·의미 판단·추론 사슬·단일 원인 추적(sonnet 기본) / `high` 위 "high를 올리는 조건"에 해당하는 검증·반증·판정(sonnet은 올림, opus는 기본) / `xhigh`·`max` 쓰지 않는다 — 필요해 보이면 먼저 작업을 쪼갠다. 최상위 effort는 비용 대비 이득이 입증되기 전까지 기본값으로 두지 않는다.

**실행 중 상향 대신 에스컬레이션**
에이전트가 조사 중 심각·Critical 사항을 발견했다고 그 자리에서 모델·effort를 올리지 않는다(실행 중 상향은 불가능하기도 하다). 발견한 에이전트는 보고 끝에 `에스컬레이션: <사유·위치·근거>` 를 남기고, 오케스트레이터가 그 건만 `deep-reasoner`(opus, high)나 `verifier` 로 별도 투입해 보완한다. 발견과 심화를 분리하면 얕은 에이전트가 넓게 훑고 비싼 에이전트는 필요한 곳에만 쓴다.

**티어 에이전트 정의** (`agents/`, frontmatter에 `model`·`effort` 고정)
| 에이전트 | 모델 | effort | 용도 |
|---|---|---|---|
| `scout` | haiku | low | 수집·추출 (읽기 전용) |
| `worker` | sonnet | medium | 기본 조사·구현·검토 (Edit/Write 보유 — "수정 금지" 분석에는 `verifier`) |
| `verifier` | sonnet | high | 검증·반증, 실행 확인이 핵심인 분석 (Edit/Write 없음, Bash 가능) |
| `deep-reasoner` | opus | high | 에스컬레이션 건·결과 불일치 판정·부수 발견이 필요한 심화 분석 (Edit/Write 없음, Bash 가능) |

**서브 에이전트 제약 준수** — 실측에서 `worker`(sonnet medium) 1건이 "소스 직접 수정 금지"를 어기고 임시 수정 후 복구했다(`verifier`·`deep-reasoner` 위반 0건).
- 금지·읽기 전용 제약은 프롬프트 첫 부분에 쓰고, 도구 집합이 이를 줄이는 에이전트를 고른다(분석 전용이면 Edit/Write 가 없는 `verifier`·`deep-reasoner`). 단 이들도 Bash 로 파일을 만들 수 있다 — 실측에서 테스트 파일을 추가했다. 도구 집합은 방어선 하나일 뿐이므로 아래 사후 점검을 함께 쓴다.
- 제약이 중요한 실행은 끝난 뒤 오케스트레이터가 사후 점검한다: 대상 파일 해시를 원본과 대조, 원본 저장소 `git status --short` 가 비어 있는지 확인, 전사에서 금지 경로 접근 여부 검색.
- 위반이 확인되면 그 실행 결과를 증거에서 제외하거나 위반을 명시해 보고한다.

**effort를 지정하는 방법**
- `Workflow`: `agent(prompt, { model, effort })` 로 호출 단위 지정. 모델과 한 쌍으로 항상 같이 쓴다.
- `Agent` 툴: 호출 파라미터에 `effort`가 **없다**(`model`만 있음). 지정하지 않으면 세션 설정(`settings.json` 의 `modelSettings`)을 따른다. 호출마다 effort를 가르려면 `Workflow` 를 쓰거나, 위 티어 에이전트(`subagent_type`)를 고른다. 에이전트 정의 frontmatter의 `effort` 는 **적용됨을 확인했다**(2026-10-06: `worker`→`medium`, `verifier`→`high` 가 서브에이전트 전사 `subagents/agent-*.jsonl` 의 `"effort"`·`"perTurnEffort"` 필드에 턴마다 기록). 새로 만든 에이전트 정의는 **세션 시작 시점에 레지스트리에 올라가므로 새 세션부터** 쓸 수 있다.
- 적용 여부는 서브에이전트 전사의 `"effort"` 필드로 확인한다. (실측 근거는 git 이력의 이 절에 있다.)

**속도에 대한 오해**
에이전트의 벽시계 시간은 토큰 생성이 아니라 **도구 왕복 횟수**가 지배한다(`rg`·DB 쿼리·파일 읽기마다 고정 비용). 따라서 모델을 낮춰도 체감 단축은 크지 않다. 단, effort는 추론 토큰량을 직접 바꾸므로 모델 하향보다 소요 시간에 더 영향을 줄 수 있다. haiku의 실익은 속도보다 **비용과 병렬 처리량**이다 — 동시 실행이 `min(16, 코어수-2)`로 묶여 있어, 에이전트가 싸면 같은 예산으로 부채살을 넓게 편다.

**재시작 비용**
이미 실행 중인 워크플로의 모델을 바꾸려면 중단 → 스크립트 수정 → `resumeFromRunId`로 재개해야 하며, `(prompt, opts)`가 바뀐 에이전트는 캐시가 깨져 다시 돈다. 이득이 작으면 재시작하지 말고 다음 실행부터 적용한다.

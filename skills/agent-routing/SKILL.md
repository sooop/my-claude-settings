### 서브 에이전트 모델·effort 선택

근거 데이터는 `measurements.md`(2026-10-08 실측: 3라운드·327건·25개 과제 유형). 요약: **정답이 객관적으로 확인되는 일에서 Haiku 5.5 는 Sonnet 5.5 와 정확도가 같고 비용은 약 1/16 이다.**
모델을 비워 두면 기본은 **sonnet** 이다(CLAUDE.md). `Workflow` 의 `agent()` 는 모델을 비우면 세션 모델(opus)을 상속하므로 **항상 명시한다.**

**함정 — `haiku` 별칭은 Haiku 4.5 다.** 4.5 는 5.5 보다 느리고(약 3배) 건당 비용이 Sonnet 수준($0.066 대 $0.005)이며 정확도도 낮았다. 5.5 는 전체 ID `claude-haiku-5-5` 로만 지정된다.
- `Agent` 툴: `model` enum 에 5.5 가 없다 → **티어 에이전트(`scout`·`builder`)로 쓴다.** `model:'haiku'` 를 쓰지 않는다.
- `Workflow`: `agent(p, { model: 'claude-haiku-5-5', effort: 'medium' })`.
- 에이전트 정의 frontmatter: `model: claude-haiku-5-5` (새 프로세스에서 적용 확인).

#### 1차 기준: 완료를 객관적으로 확인할 수 있는가

| 작업 | 담당 | 모델·effort |
|---|---|---|
| 수집·열거·집계·정의 위치·호출 사슬 추적(10단계까지)·정해진 기준 대조·파일 단위 코드리뷰 1차·Medium 이하 지적의 반증 | `scout` | haiku 5.5 · medium |
| 범위와 완료 조건이 명확한 구현·수정·일괄 리팩터(테스트·명령 출력으로 확인), 실패 테스트 수정, 사양이 명시된 함수 구현 | `builder` | haiku 5.5 · medium |
| 요구가 모호하거나 열린 탐색, 설계 판단, 여러 결과의 종합, 사용자에게 가는 최종 결론, 부수 발견 보고의 신뢰가 중요한 조사 | `worker` | sonnet · medium |
| High 이상 지적의 검증·반증, 실행으로 근거를 확인하는 일 | `verifier` | sonnet · high |
| 에스컬레이션 건, sonnet(high) 결과 불일치의 판정 | `deep-reasoner` | opus · high |

- **같은 일이면 haiku 로 시작한다.** 부채살(fan-out) 규모가 클수록 이득이 크다 — 같은 예산으로 약 16배 넓게 편다.
- **승격 규칙(위로만).** haiku 결과가 ① 검증 실패(테스트·재실행) ② 형식 위반 ③ 같은 입력에서 엇갈림 중 하나면 같은 입력을 sonnet medium 으로 다시 돌린다. haiku 비용이 1/16 이라 재투입도 싸다.
- **크기.** 에이전트 1건의 입력 컨텍스트는 10만 토큰 이하로 쪼갠다. Haiku 5.5 는 프롬프트 10만 토큰 초과 시 단가가 5배(여전히 sonnet 의 1/4)이고 그 구간의 정확도는 미검증이다. 1,200파일 집계처럼 큰 범위도 `rg` 로 좁히면 문제없었다.
- **Sonnet 이 나은 경우는 못 찾았다.** 이유를 붙여 sonnet 을 고를 수 있는 근거는 "모호함·종합·사용자 대면 결론"뿐이다(미검증 영역, 아래).

#### effort 고정

- **haiku 5.5: `medium` 고정.** `low` 는 정확도는 같지만 대규모 작업이 느리고(1,200파일 집계 145s 대 73s) **부수 취약점 에스컬레이션을 3회 중 1회만 보고**했다. `high` 는 이득 없이 출력 토큰만 약 1.6배다.
- **sonnet: `medium` 기본.** `high` 는 아래 조건에서만(점수가 아니라 비용을 쓰는 결정이므로 근거를 남긴다): 같은 입력에서 medium 결과가 엇갈림 / 오판 비용이 큼(High 이상 검증, 되돌릴 수 없는 변경의 근거) / 결론의 근거를 실행으로 확인하는 일이 핵심.
- **opus: `high`(기본).** `xhigh`·`max` 는 쓰지 않는다 — 필요해 보이면 작업을 쪼갠다.

#### opus — 좁은 예외 (이번에도 우위 관찰 0)

R2·R3 에서 opus 는 sonnet 과 정확도가 같았고 비용은 2.4배(haiku 5.5 의 약 38배)였다. 단순 열거·추적·체크리스트·단일 원인 추적에는 쓰지 않는다. 아래에만 쓴다.
1. sonnet(high) 결과가 서로 엇갈려 판정이 필요한 경우.
2. 오판 비용이 큰 Critical 건의 재검증 — 보안 경계, 동시성 정합성, 되돌릴 수 없는 데이터 변경.
3. 정답 외의 부수 발견이 필요한 심화 분석(영향 범위·설계 의문·전제 조건) — 정확도가 아니라 보고의 폭을 사는 것이며 시간이 약 1.4배 이상 든다.

상향 조건은 추정이 아니라 관찰이다. 새 유형이 의심되면 같은 입력을 sonnet(high)·opus 에 돌려 결론이 갈릴 때만 그 유형을 opus 목록에 올린다. **원인이 둘이거나 증상이 엉뚱한 곳을 가리키는 문제**는 이번에 시험했고(다중 원인 디버깅 15/15 정답, 전 조건) 결과가 갈리지 않았다.

#### 심각도 기반 배분

검증·반증처럼 항목마다 오판 비용이 다른 단계는 심각도로 가른다. 심각한 지적을 잘못 기각하면 결함이 남으므로 그쪽에만 비용을 더 쓴다.
```js
const opts = f.severity === 'Critical' ? { model: 'opus', effort: 'high' }
           : f.severity === 'High'     ? { model: 'sonnet', effort: 'high' }
           :                             { model: 'claude-haiku-5-5', effort: 'medium' }
```

#### 출력 형식

Haiku 는 구조화 스키마의 값 필드에 값만 넣는 비율이 낮았다(엄격 일치 0.6 대 sonnet 0.83) — **내용은 맞고 형식을 어긴다.** 프롬프트에 "각 필드에는 값만, 설명은 `note` 필드에"를 쓰고, 오케스트레이터는 필요하면 포함 매칭으로 읽는다. 에이전트 결과를 정확 일치로 곧바로 파싱하지 않는다.

#### 실행 중 상향 대신 에스컬레이션

에이전트가 조사 중 심각·Critical 사항을 발견했다고 그 자리에서 모델·effort를 올리지 않는다(실행 중 상향은 불가능하기도 하다). 발견한 에이전트는 보고 끝에 `에스컬레이션: <사유·위치·근거>` 를 남기고, 해당 사항이 없으면 `에스컬레이션: 없음` 이라고 쓴다(빠뜨림과 구별된다). 오케스트레이터가 그 건만 `deep-reasoner`(opus, high)나 `verifier` 로 별도 투입해 보완한다. 발견과 심화를 분리하면 얕고 싼 에이전트가 넓게 훑고 비싼 에이전트는 필요한 곳에만 쓴다.
실측: 무관한 취약점(`eval`·SQL 인젝션·하드코딩 키)을 심은 프로젝트에서 에스컬레이션을 보고한 비율은 haiku medium 3/3, haiku low 1/3, sonnet medium 2/3, sonnet high 3/3, opus 3/3 — 어느 티어도 100% 신뢰할 수 없으므로 에스컬레이션이 중요한 일은 **지시문에 규칙을 넣고 `에스컬레이션: 없음` 까지 쓰게** 한다.

#### 티어 에이전트 정의 (`agents/`, frontmatter 에 `model`·`effort` 고정)

| 에이전트 | 모델 | effort | 용도 |
|---|---|---|---|
| `scout` | haiku 5.5 | medium | 수집·추적·집계·기준 대조 (읽기 전용) |
| `builder` | haiku 5.5 | medium | 범위·완료 조건이 명확한 구현·수정 (Edit/Write 보유) |
| `worker` | sonnet | medium | 모호하거나 판단·종합이 필요한 조사·구현·검토 (Edit/Write 보유 — "수정 금지" 분석에는 `verifier`) |
| `verifier` | sonnet | high | High 이상 검증·반증, 실행 확인이 핵심인 분석 (Edit/Write 없음, Bash 가능) |
| `deep-reasoner` | opus | high | 에스컬레이션 건·결과 불일치 판정·부수 발견이 필요한 심화 분석 (Edit/Write 없음, Bash 가능) |

새로 만들거나 바꾼 에이전트 정의는 **세션 시작 시점에 레지스트리에 올라가므로 새 세션부터** 적용된다(같은 세션에서는 이전 정의로 실행된다 — 실측). 적용 여부는 전사 `agent-*.jsonl` 의 `message.model`·`"effort"` 로 확인한다. 새 프로세스로 빠르게 확인하려면 `claude -p "…" --agent scout --output-format json | jq '.modelUsage|keys'`.

#### 서브 에이전트 제약 준수

- 금지·읽기 전용 제약은 프롬프트 첫 부분에 쓰고, 도구 집합이 이를 줄이는 에이전트를 고른다(분석 전용이면 Edit/Write 가 없는 `scout`·`verifier`·`deep-reasoner`). 단 이들도 Bash 로 파일을 만들 수 있다 — 도구 집합은 방어선 하나일 뿐이다.
- 실측: 읽기 전용 지시 과제 12회(haiku 4.5·5.5, sonnet, opus 전 조건) 위반 0건. 과거 `worker`(sonnet medium) 1건이 "소스 직접 수정 금지"를 어기고 임시 수정 후 복구한 사례가 있어 사후 점검은 유지한다.
- 제약이 중요한 실행은 끝난 뒤 오케스트레이터가 사후 점검한다: 대상 파일 해시를 원본과 대조, 원본 저장소 `git status --short` 가 비어 있는지 확인, 전사에서 금지 경로 접근 여부 검색.
- 위반이 확인되면 그 실행 결과를 증거에서 제외하거나 위반을 명시해 보고한다.

#### effort를 지정하는 방법

- `Workflow`: `agent(prompt, { model, effort })` 로 호출 단위 지정. 모델과 한 쌍으로 항상 같이 쓴다. Haiku 4.5 는 effort 를 기록하지 않지만 5.5 는 적용된다(전사 `"effort"` 필드 확인).
- `Agent` 툴: 호출 파라미터에 `effort` 가 **없다**(`model` 만 있음). 호출마다 effort 를 가르려면 `Workflow` 를 쓰거나 티어 에이전트(`subagent_type`)를 고른다.

#### 속도·재시작

- 에이전트의 벽시계 시간은 토큰 생성이 아니라 **도구 왕복 횟수**가 지배한다. 실측: haiku 5.5 평균 27s ≈ sonnet 25s ≪ haiku 4.5 75s. 즉 5.5 로 바꾸는 이득은 속도가 아니라 **비용(1/16)과 병렬 처리량**이다 — 동시 실행이 `min(16, 코어수-2)` 로 묶여 있어 에이전트가 싸면 같은 예산으로 부채살을 넓게 편다.
- 이미 실행 중인 워크플로의 모델을 바꾸려면 중단 → 스크립트 수정 → `resumeFromRunId` 로 재개해야 하며, `(prompt, opts)` 가 바뀐 에이전트는 캐시가 깨져 다시 돈다. 이득이 작으면 다음 실행부터 적용한다.

#### 아직 모르는 것 (측정 전에는 sonnet 쪽으로 기운다)

요구가 모호한 과제, 수십 단계의 장기 에이전트 루프, 수십만 줄 실제 코드베이스, 동시성·타이밍 버그, 장문 보고서 품질, 10만 토큰 초과 컨텍스트. 이런 일을 haiku 에 맡기려면 먼저 `bench/` 로 같은 과제를 sonnet 과 나란히 돌려 갈리는지 본다(재현 방법: `measurements.md` 맨 아래). 새 모델이 나올 때도 같은 하니스로 다시 잰다.

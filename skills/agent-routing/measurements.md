## 발견

1. **정확도 천장.** 25개 과제 유형에서 Haiku 5.5(low~high)·Sonnet 5.5(medium·high)·Opus 5.5 가 사실상 구분되지 않았다. 호출 사슬 10단계, 디스패치 테이블, 다중 원인 디버깅, 21개 숨김 테스트 구현, 36파일 리팩터까지 포함한다. **이 실측은 Sonnet 이 Haiku 5.5 를 이기는 과제를 찾지 못했다.** Opus 는 이번에도 Sonnet 대비 우위가 0 이고 비용은 2.4배(Sonnet 대비), Haiku 5.5 대비 약 38배였다.
2. **`haiku` 별칭(4.5)은 열위.** R1 에서 정확도가 낮고(0.95: 바늘 찾기·리뷰·반증 오답), 도구 호출이 많아 느리며(E2 152s, E3 409s 대 Haiku 5.5 8~23s), 건당 비용이 Sonnet 에 근접($0.066). 한국어 출력이 깨지는(mojibake) 사례도 있었다. 기존 `scout` 가 이것이었다.
3. **effort.** Haiku 5.5 의 high 는 정확도 이득이 없고 출력 토큰만 약 1.6배(R1 평균 2252 대 1418, V 과제는 7.5k). low 는 정확도는 같으나 대규모 집계(1,200파일)에서 느렸고(145s 대 medium 73s, sonnet 22~46s), **부수 취약점 에스컬레이션을 3회 중 1회만 보고**했다(medium 3/3, sonnet medium 2/3, sonnet high 3/3, opus 3/3). → Haiku 는 medium 고정.
4. **형식 준수.** 구조화 스키마의 값 필드에 정답만 넣는 비율(엄격 일치, 사슬·바늘 과제): Sonnet 0.83, Haiku 5.5 low 0.62 / medium 0.58 / high 0.21, Haiku 4.5 0.25. Haiku 는 값 자리에 설명문을 써 내용은 맞고 형식은 어긴다. 오케스트레이터가 정확 일치로 파싱하면 오답으로 처리된다. 프롬프트에 "각 필드에는 값만"을 쓰거나 포함 매칭으로 읽는다.
5. **출력량.** Sonnet 의 출력 토큰은 Haiku 5.5 의 약 절반. 비용 차이(약 16배)는 단가가 지배한다.
6. **읽기 전용 제약 위반 0건**(P 과제 12회, 전 조건). 도구 집합이 같아도 이번 실측에서 Haiku 5.5 는 위반하지 않았다. 사후 점검 규칙은 유지한다.

## 한계 (미검증)

- 모두 사양이 명확하고 정답이 객관적인 합성 과제다. **요구가 모호한 과제, 수십 단계의 장기 에이전트 루프, 대규모 실제 코드베이스(수십만 줄), 동시성·타이밍 버그, 장문 보고서의 품질**은 시험하지 않았다. 천장 효과 때문에 "차이가 없다"는 "차이가 없음이 입증됨"이 아니라 "이 난이도에서는 못 찾음"이다.
- 반복이 2~3회라 드문 실패(1/20 이하)는 보이지 않는다.
- 컨텍스트가 10만 토큰을 넘는 일에서 Haiku 5.5 의 정확도·단가(5배)는 시험하지 않았다.

## 재현

`bench/` 의 `gen.py`·`gen2.py`·`gen3.py` 가 코퍼스와 숨김 테스트를 만들고(파일 상단 `ROOT` 가 작업 폴더), `wf-round{1,2,3}.js` 가 Workflow 스크립트(`B` 상수를 작업 폴더로 바꾼다),
`score*.py <워크플로 전사 폴더>` 가 채점해 `rows*.json` 을 만들고 `cost.py` 가 비용을, `agg*.py` 가 표를 만든다. 코퍼스 생성은 시드 고정이라 결정적이다. 새 모델이 나오면 `COND` 만 바꿔 같은 과제를 다시 돌린다.
(Windows: 시스템 `PYTHONHOME` 이 어긋나 있으면 `unset PYTHONHOME; python -I -X utf8 ...`.)

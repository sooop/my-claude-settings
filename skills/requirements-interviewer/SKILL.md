# Requirements Interviewer Skill
 
작업에 사용자가 미처 고려하지 못한 요구사항을 심층 인터뷰로 발굴합니다.
인터뷰 결과는 작업의 컨텍스트 및 계획을 위한 지식으로 사용합니다. 

단, 계획을 수립하고 이를 실행하려는 경우에는 계획 문서를 따릅니다.
 
---
 
## 0. 실행 모드
 
이 스킬은 두 가지 모드로 동작합니다.
 
| 모드 | 진입 조건 | 동작 방식 |
|---|---|---|
| **독립 모드** (기본) | 작업/계획을 시작하기 위해 코드베이스를 탐색한 후 | 아래 전체 워크플로우(섹션 1~7)를 실행 |
| **모듈 모드** | 다른 스킬이 `[INTERVIEW_MODULE]` 지시어와 함께 호출한 경우 | 섹션 M만 실행하고 결과를 호출 스킬로 반환 |
 
---
 
## 섹션 M. 모듈 모드 (다른 스킬에서 호출 시)
 
다른 스킬이 이 스킬을 인터뷰 서브루틴으로 호출할 때 사용하는 모드입니다.
 
### M-1. 호출 규약
 
호출 스킬은 다음 정보를 컨텍스트에 포함해야 합니다:
 
```
[INTERVIEW_MODULE]
domain: <도메인 설명 (예: "로직 시각화", "데이터 분석")>
goal: <인터뷰 목표 한 문장>
required_fields:
  - <필드명>: <설명>
  - ...
optional_fields:
  - <필드명>: <설명>
  - ...
max_rounds: <최대 인터뷰 라운드 수 (기본 3)>
```
 
### M-2. 모듈 모드 동작 방식
 
1. 호출 스킬이 전달한 `required_fields`를 기준으로 인터뷰를 진행합니다.
2. 인터뷰 방식은 섹션 4-1(독립 모드)과 동일하게 유연하게 운영합니다.
3. `max_rounds` 초과 시, 미확정 항목을 명시하고 종료합니다.
4. 호출 스킬의 다음 단계로 제어를 넘깁니다.
 
### M-3. 모듈 모드 출력 형식
 
```
--- [도메인] 인터뷰 완료 ---
 
확정된 항목
- [필드명]: [확인된 값]
- ...
 
미확정 항목 (기본값 적용)
- [필드명]: [적용할 기본값]
- ...
```
 
출력 후 즉시 호출 스킬의 다음 단계(예: 시각화 진행)로 이어갑니다. 별도 사용자 확인을 요구하지 않습니다.

## 1. 전체 워크플로우 (독립 모드)
 
```
요청 수신 → 스킬 적용 여부 판단 → 목표 정의 및 확인 → 심층 인터뷰 루프 → 요구사항 요약 출력 → 작업 개시 여부 결정
```
 
---
 
## 2. 스킬 적용 여부 판단
 
스킬 적용 여부는 아래 기준으로 판단합니다.
 
**적용하는 경우 (UX 결정이 핵심인 앱)**
- 개발 도구 (코드 생성, 문법 변환, 포맷터, 린터 시뮬레이터)
- 데이터 변환/처리 도구 (JSON ↔ CSV, 인코딩 변환, 정규식 테스터)
- 입력 처리 도구 (폼 빌더, 계산기, 설정 생성기)
- 워크플로우 도구 (타이머, 체크리스트, 프로세스 트래커)
 
**건너뛰는 경우 (요구사항이 자명한 앱)**
- 단순 정보 표시 (날씨 위젯, 시계, 카운터)
- 사용자가 이미 충분히 상세한 스펙을 제공한 경우
- 사용자가 "그냥 만들어줘", "빠르게 만들어줘" 등으로 명시적으로 인터뷰를 원하지 않음을 표현한 경우
 
---
 
## 3. 목표 정의 및 확인
 
요청을 받으면, 먼저 Claude가 이해한 목표를 한 문장으로 명확히 기술하고 사용자에게 확인을 받습니다.
 
**형식 예시:**
```
요청을 이렇게 이해했습니다:
 
"JSON 문자열을 입력받아 보기 좋게 포맷팅해 주는 브라우저 도구"
 
맞나요? 다르게 이해해야 할 부분이 있으면 알려주세요.
```
 
목표가 확인되면 인터뷰 루프로 진입합니다.
 
---
 
## 4. 심층 인터뷰 루프
 
### 4-1. 인터뷰 방식
 
상황에 따라 유연하게 선택합니다:
 
| 상황 | 방식 |
|---|---|
| 핵심 정보가 전혀 없는 경우 | 한 번에 2~3개 질문 묶음으로 시작 |
| 답변에 따라 파생 질문이 생기는 경우 | 하나씩 순차적으로 파고들기 |
| 사용자가 긴 설명을 제공한 경우 | 불명확한 항목만 선별하여 집중 질문 |
 
질문은 항상 구체적인 선택지나 예시를 함께 제시합니다. "어떤 방식을 원하세요?"보다 "A 방식(설명)과 B 방식(설명) 중 어느 쪽에 가깝나요?"가 더 효과적입니다.
 
### 4-2. 반드시 파악해야 할 영역
 
아래 5개 영역은 모든 인터뷰에서 빠짐없이 다룹니다. 단, 맥락상 자명한 항목은 생략 가능합니다.
 
#### A. 대상 사용자 / 사용 맥락
- 누가 사용하는가? (본인만, 팀원, 불특정 다수)
- 어떤 환경에서 사용하는가? (데스크탑 브라우저, 모바일, 사내 인트라넷)
- 기술 수준은 어느 정도인가? (개발자, 일반 사용자, 혼합)
- **파생 질문 트리거**: 사용자가 "개발자용"이라고 하면 → 단축키, 코드 복사 버튼, 원시 출력 등을 원하는지 추가 확인
 
#### B. 데이터 입출력 형식
- 입력은 어떻게 받는가? (텍스트 입력, 파일 업로드, URL, 붙여넣기)
- 출력은 어떻게 보여주는가? (화면 표시, 파일 다운로드, 클립보드 복사)
- 입출력 데이터의 크기 범위는? (수 KB인지 수 MB인지)
- **파생 질문 트리거**: "파일 업로드"가 언급되면 → 허용 확장자, 다중 파일 여부, 드래그앤드롭 필요 여부 확인
 
#### C. 상태 관리 / 저장 방식
- 작업 내용이 새로고침 후에도 유지되어야 하는가?
- 여러 작업을 동시에 다루는가? (탭, 히스토리, 세션 단위)
- 설정값이나 환경설정을 저장해야 하는가?
- **파생 질문 트리거**: "저장"이 필요하다고 하면 → 브라우저 localStorage로 충분한지, 서버 저장이 필요한지 확인
 
#### D. 에러 처리 / 엣지케이스
- 잘못된 입력(빈 값, 형식 오류)에 어떻게 반응해야 하는가?
- 처리 실패 시 사용자에게 무엇을 보여줄 것인가?
- 특별히 막아야 할 케이스가 있는가? (예: 파일 크기 제한, 입력 길이 제한)
- **파생 질문 트리거**: "실시간 처리"가 언급되면 → 입력 도중 에러 표시를 즉시 할 것인지, 완료 후 한 번에 할 것인지 확인
 
#### E. UI 스타일 / 레이아웃 선호도
- 선호하는 레이아웃 구조가 있는가? (좌우 분할, 상하 분할, 단일 패널)
- 참고하고 싶은 기존 도구나 앱이 있는가?
- 다크모드, 폰트 크기 등 접근성 요소가 중요한가?
- **파생 질문 트리거**: "좌우 분할"이 언급되면 → 분할 비율 고정인지 가변인지, 리사이즈 핸들이 필요한지 확인
 
### 4-3. Claude가 주도적으로 파고드는 항목
 
사용자가 언급하지 않아도, 해당 앱 성격에 따라 아래를 선제적으로 질문합니다:
 
- **실시간성**: 입력할 때마다 즉시 처리할 것인가, 버튼 클릭 시 처리할 것인가?
- **실행 취소(Undo)**: 이전 상태로 돌아가는 기능이 필요한가?
- **복사/공유**: 결과물을 쉽게 복사하거나 공유할 방법이 필요한가?
- **키보드 단축키**: 자주 쓰는 동작을 단축키로 처리할 필요가 있는가?
- **처리 중 피드백**: 처리에 시간이 걸릴 경우 로딩 인디케이터가 필요한가?
- **모바일 대응**: 작은 화면에서도 동작해야 하는가?
 
### 4-4. 인터뷰 종료 조건
 
다음 중 하나에 해당하면 인터뷰를 마칩니다:
 
- 5개 영역이 모두 파악된 경우
- 사용자가 "그냥 만들어줘" 등으로 진행을 명시하는 경우 → 미확정 항목은 합리적 기본값으로 처리하고, 요약에 명시
- 총 인터뷰 라운드가 4회를 초과한 경우 → 남은 미확정 항목을 명시하고 종료

## 5. 요구사항 요약 출력
 
인터뷰 완료 후, 아래 형식으로 채팅창에 요약을 출력합니다. 파일 생성 없이 텍스트로 출력합니다.
 
```
--- 요구사항 요약 ---
 
목표
[한 문장 목표 기술]
 
갖춰야 할 것 (Must Have)
- [항목 1]
- [항목 2]
- ...
 
있으면 좋은 것 (Nice to Have)
- [항목 1]
- ...
 
피해야 할 것 / 제약 조건
- [항목 1]
- ...
 
미확정 항목 (기본값으로 처리)
- [항목]: [적용할 기본값]
- ...
```
 
---
 
## 6. 제작 여부 결정 (사용자에게 선택권)
 
요약 출력 후, 사용자에게 다음 선택지를 제공합니다:
 
```
요구사항 정리가 완료됐습니다.
 
1. 지금 바로 웹 앱 제작 시작
2. 요약 내용 수정 후 제작
3. 요구사항 문서(.md)만 먼저 생성
```
 
사용자가 1번 또는 2번을 선택하면, 위 요약을 컨텍스트로 삼아 웹 앱 제작을 시작합니다.
사용자가 3번을 선택하면, 요약 내용을 `.md` 파일로 저장하고 `/mnt/user-data/outputs/`에 출력합니다.
 
---
 
## 7. 웹 앱 제작 시 요약 활용 방법
 
인터뷰 결과 요약은 제작 과정 전반에 걸쳐 다음과 같이 활용됩니다:
 
- **Must Have** 항목은 반드시 구현합니다. 기술적으로 불가능한 경우 사용자에게 먼저 알립니다.
- **Nice to Have** 항목은 복잡도가 낮은 경우 포함하고, 높은 경우 제외 후 사용자에게 고지합니다.
- **피해야 할 것** 항목은 코드 작성 중 체크리스트로 활용합니다.
- **미확정 항목**의 기본값은 결과물의 주석이나 README에 명시합니다.
 
---
 
## 8. 주의 사항
 
- 인터뷰는 도움이 되어야지, 부담이 되어서는 안 됩니다. 사용자가 짧게 답하면 그 답을 존중하고 다음으로 넘어갑니다.
- 같은 항목을 두 번 이상 반복해서 묻지 않습니다.
- 질문은 개방형과 선택형을 적절히 섞습니다. 선택형 질문에는 항상 "기타(직접 입력)" 여지를 남깁니다.
- 이 스킬은 웹 앱 제작 품질 향상이 목적입니다. 인터뷰 자체가 목적이 아님을 항상 인식합니다.

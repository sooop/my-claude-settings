# Requirements Interviewer Skill

웹 앱·도구, 문서·자료를 만들기에 앞서, 요구사항의 공백을 명확도에 맞는 수준의 질문으로 메웁니다. 명확한 요청에는 질문하지 않습니다.
인터뷰 결과는 곧바로 제작의 컨텍스트로 활용됩니다.

---

## 0. 실행 모드

이 스킬은 두 가지 모드로 동작합니다.

| 모드 | 진입 조건 | 동작 방식 |
|---|---|---|
| **독립 모드** (기본) | 사용자가 직접 웹앱·도구 또는 문서·자료 제작을 요청한 경우 | 아래 전체 워크플로우(섹션 1~8)를 실행 |
| **모듈 모드** | 다른 스킬이 `[INTERVIEW_MODULE]` 지시어와 함께 호출한 경우 | 섹션 M만 실행하고 결과를 호출 스킬로 반환 |

---

## 섹션 M. 모듈 모드 (다른 스킬에서 호출 시)

다른 스킬이 이 스킬을 인터뷰 서브루틴으로 호출할 때 사용하는 모드입니다.

### M-1. 호출 규약

호출 스킬은 다음 정보를 컨텍스트에 포함해야 합니다:

```
[INTERVIEW_MODULE]
domain: <도메인 설명 (예: "로직 시각화", "데이터 분석")>
goal: <인터뷰 목표 한 문장>
required_fields:
  - <필드명>: <설명>
  - ...
optional_fields:
  - <필드명>: <설명>
  - ...
max_rounds: <최대 인터뷰 라운드 수 (기본 3)>
```

### M-2. 모듈 모드 동작 방식

1. 호출 스킬이 전달한 `required_fields`를 기준으로 인터뷰를 진행합니다.
2. 인터뷰 방식은 섹션 4-1(독립 모드)과 동일하게 유연하게 운영합니다.
3. `max_rounds` 초과 시, 미확정 항목을 명시하고 종료합니다.
4. 인터뷰 완료 후 아래 형식으로 **채팅창에 요약을 출력**(코드 블록 없이 일반 마크다운으로, 이모지 없이)하고, 호출 스킬의 다음 단계로 제어를 넘깁니다.

### M-3. 모듈 모드 출력 형식

```
--- [도메인] 인터뷰 완료 ---

확정된 항목
- [필드명]: [확인된 값]
- ...

미확정 항목 (기본값 적용)
- [필드명]: [적용할 기본값]
- ...
```

출력 후 즉시 호출 스킬의 다음 단계(예: 시각화 진행)로 이어갑니다. 별도 사용자 확인을 요구하지 않습니다.

## 1. 전체 워크플로우 (독립 모드)

```
요청 수신 → 작업 종류·명확도 판정(섹션 2) → [1단계] 바로 제작 / [2단계] 핵심 질문 1~4개 후 제작 / [3단계] 심층 인터뷰 후 제작 → 요약 → 제작
```

---

## 2. 작업 종류와 명확도 판정 (3단계)

마저 작업 종류를 정합니다. 웹앱·도구(실행되는 화면이나 기능)는 4-2의 웹앱·도구 프로필을, 문서·자료(읽거나 발표하거나 계산하는 산출물)는 4-2b의 문서·자료 프로필을 씁니다. 둘이 섞인 요청은 두 프로필에서 필요한 영역만 고릅니다.

다음으로 아래 기준으로 단계를 정합니다. 단계는 질문 횟수가 아니라, 답을 몰라서 결과물이 크게 달라지는 지점이 얼마나 되는가로 판정합니다.

| 단계 | 판정 기준 | 동작 |
|---|---|---|
| 1. 명확 | 입출력과 동작이 자명한 단순 앱(시계, 카운터, 단순 정보 표시), 독자·분량·형식이 자명한 짧은 문서, 상세 스펙이나 목차·초안이 이미 제공됨, "그냥 만들어줘" 등 인터뷰를 원치 않는다는 표현 | 질문 없이 바로 제작합니다. 가정한 내용은 결과물 설명이나 README에 명시합니다. |
| 2. 보통 | UX를 좌우하는 미정 사항이 1~4개 | 핵심 질문 1~4개를 한 번에 묻고 제작합니다. |
| 3. 복잡 | 미정 사항이 5개 이상이거나, 입출력·저장·상태 관리가 얽혀 있거나, 여러 화면·기능이나 긴 분량·다중 문서로 규모가 크거나, 독자가 여럿라서 요구가 갈리거나, 요청이 모호하거나 서로 모순됨 | 섹션 4의 심층 인터뷰를 한 뒤 제작합니다. |

**UX 결정이 핵심이 되는 앱 유형 (2~3단계로 올라가기 쉬움)**
- 개발 도구 (코드 생성, 문법 변환, 포맷터, 린터 시뮬레이터)
- 데이터 변환/처리 도구 (JSON ↔ CSV, 인코딩 변환, 정규식 테스터)
- 입력 처리 도구 (폼 빌더, 계산기, 설정 생성기)
- 워크플로우 도구 (타이머, 체크리스트, 프로세스 트래커)

**독자·목적에 따라 결과가 크게 달라지는 문서 유형 (2~3단계로 올라가기 쉬움)**
- 보고서, 제안서, 기획서, 정책·규정 문서
- 가이드, 매뉴얼, 교육 자료
- 발표 슬라이드, 요약·브리핑 자료
- 스프레드시트 모델, 분석 보고서

**판정 규칙**
- 판단이 애매하면 2단계로 처리합니다.
- 이미 대화에서 답한 내용은 다시 묻지 않습니다.
- 사용자가 자리에 없는 경우(예약 실행, 부재 중 등)에는 질문하지 않고 1단계로 진행하며, 가정한 내용을 결과물 첫머리에 명시합니다. 되돌릴 수 없고 선택이 갈리는 결정만 예외입니다.
- 아래 요청에는 이 스킬을 적용하지 않습니다: 기존 소스코드·아티팩트·문서 파일의 수정·복제, 채팅 답변으로 충분한 요약·설명·질의응답, 형식과 절차가 고정된 전용 스킬이 맡는 요청(시험 답안, 답안 감사, 완전 가이드, 띄어쓰기 판정 등).

---

## 3. 목표 확인 방식

Claude가 이해한 목표를 한 문장으로 밝히되, 사용자의 확인을 기다리는 별도 라운드는 두지 않습니다.

- 2~3단계: 첫 질문 묶음 앞에 "이렇게 이해했습니다: ..." 한 줄을 붙이고 이어서 질문합니다.
- 1단계: 제작 결과를 설명할 때 이해한 목표와 가정을 함께 밝힙니다.
- 이해가 어긋났다면 질문 답변이나 후속 수정 요청에서 바로잡습니다.

---

## 4. 심층 인터뷰 루프 (3단계 전용)

2단계(핵심 질문)에서는 이 섹션 전체를 실행하지 않고, 4-2·4-2b 중 해당 프로필의 영역에서 결과물을 가장 크게 갈라놓는 항목만 골라 한 번에 1~4개를 묻습니다.

### 4-1. 인터뷰 방식

상황에 따라 유연하게 선택합니다:

| 상황 | 방식 |
|---|---|
| 핵심 정보가 전혀 없는 경우 | 한 번에 2~3개 질문 묶음으로 시작 |
| 답변에 따라 파생 질문이 생기는 경우 | 하나씩 순차적으로 파고들기 |
| 사용자가 긴 설명을 제공한 경우 | 불명확한 항목만 선별하여 집중 질문 |

질문은 항상 구체적인 선택지나 예시를 함께 제시합니다. "어떤 방식을 원하세요?"보다 "A 방식(설명)과 B 방식(설명) 중 어느 쪽에 가깝나요?"가 더 효과적입니다.

질문은 질문 도구(AskUserQuestion)로 한 번에 1~4개씩 묻습니다. "기타" 입력은 도구가 기본 제공합니다. 질문 도구를 쓸 수 없는 환경에서는 채팅에서 같은 방식으로 묻습니다.

### 4-2. 반드시 파악해야 할 영역 (웹앱·도구 프로필)

3단계(심층 인터뷰)에서는 작업 종류에 맞는 프로필의 5개 영역을 빠짐없이 다룹니다. 단, 맥락상 자명한 항목은 생략 가능합니다. 아래는 웹앱·도구 프로필이고, 문서·자료 프로필은 4-2b에 있습니다.

#### A. 대상 사용자 / 사용 맥락
- 누가 사용하는가? (본인만, 팀원, 불특정 다수)
- 어떤 환경에서 사용하는가? (데스크탑 브라우저, 모바일, 사내 인트라넷)
- 기술 수준은 어느 정도인가? (개발자, 일반 사용자, 혼합)
- **파생 질문 트리거**: 사용자가 "개발자용"이라고 하면 → 단축키, 코드 복사 버튼, 원시 출력 등을 원하는지 추가 확인

#### B. 데이터 입출력 형식
- 입력은 어떻게 받는가? (텍스트 입력, 파일 업로드, URL, 붙여넣기)
- 출력은 어떻게 보여주는가? (화면 표시, 파일 다운로드, 클립보드 복사)
- 입출력 데이터의 크기 범위는? (수 KB인지 수 MB인지)
- **파생 질문 트리거**: "파일 업로드"가 언급되면 → 허용 확장자, 다중 파일 여부, 드래그앤드롭 필요 여부 확인

#### C. 상태 관리 / 저장 방식
- 작업 내용이 새로고침 후에도 유지되어야 하는가?
- 여러 작업을 동시에 다루는가? (탭, 히스토리, 세션 단위)
- 설정값이나 환경설정을 저장해야 하는가?
- **파생 질문 트리거**: "저장"이 필요하다고 하면 → 브라우저 localStorage로 충분한지, 서버 저장이 필요한지 확인

#### D. 에러 처리 / 엣지케이스
- 잘못된 입력(빈 값, 형식 오류)에 어떻게 반응해야 하는가?
- 처리 실패 시 사용자에게 무엇을 보여줄 것인가?
- 특별히 막아야 할 케이스가 있는가? (예: 파일 크기 제한, 입력 길이 제한)
- **파생 질문 트리거**: "실시간 처리"가 언급되면 → 입력 도중 에러 표시를 즉시 할 것인지, 완료 후 한 번에 할 것인지 확인

#### E. UI 스타일 / 레이아웃 선호도
- 선호하는 레이아웃 구조가 있는가? (좌우 분할, 상하 분할, 단일 패널)
- 참고하고 싶은 기존 도구나 앱이 있는가?
- 다크모드, 폰트 크기 등 접근성 요소가 중요한가?
- **파생 질문 트리거**: "좌우 분할"이 언급되면 → 분할 비율 고정인지 가변인지, 리사이즈 핸들이 필요한지 확인

### 4-2b. 반드시 파악해야 할 영역 (문서·자료 프로필)

적용 방식은 4-2와 같습니다. 3단계에서는 5개 영역을 빠짐없이 다루고, 2단계에서는 결과물을 가장 크게 갈라놓는 항목만 고릅니다.

#### A. 독자와 용도
- 누가 읽거나 듣는가? (본인, 팀, 의사결정자, 외부 고객, 불특정 다수)
- 읽고 무엇을 하는가? (결정, 승인, 학습, 실행, 참고용 보관)
- 독자의 배경지식 수준은? (전문가, 비전문가, 혼합)
- **파생 질문 트리거**: 독자가 "의사결정자"라면 → 결론 우선 구성, 분량 상한, 근거 수준(요약만 / 상세 부록)을 추가 확인

#### B. 범위·분량·구조
- 반드시 다룰 내용과 뿀 내용은?
- 분량이나 시간 제약은? (쪽 수, 글자 수, 발표 시간, 슬라이드 수)
- 정해진 목차나 양식, 선례가 있는가?
- **파생 질문 트리거**: "정해진 양식"이 있다고 하면 → 양식 파일이나 예시를 받을 수 있는지 확인

#### C. 근거 자료
- 제공할 자료가 있는가? (파일, 링크, 메모) 없다면 조사가 필요한가?
- 출처 표기가 필요한가? (각주, 참고문헌, 링크)
- 최신 수치나 현황이 들어가는가?
- **파생 질문 트리거**: 최신 수치·현황이 들어가면 → 기준 시점과 허용 가능한 출처 수준(공식 통계, 언론, 내부 자료)을 확인

#### D. 톤·언어·서식
- 격식 수준은? (공문, 업무 보고, 설명체, 대화체)
- 언어와 용어 규칙은? (한국어/영어, 전문용어 풀이 여부, 약어 사용)
- 서식 제약은? (표·목록 사용 여부, 강조, 이모지 금지, 폰트·여백 등 양식)
- **파생 질문 트리거**: 외부에 제출·배포한다고 하면 → 기관이나 회사의 서식 규정과 금지 표현 확인

#### E. 산출 형식과 전달 방식
- 어떤 형태가 필요한가? (채팅 답변, 편집 가능한 문서, 슬라이드, 스프레드시트, PDF)
- 이후 어떻게 쓰이는가? (직접 편집, 이메일 첨부, 인쇄, 공유 링크, 발표)
- 한 번 쓰고 끝나는지, 반복 사용할 템플릿인지?
- **파생 질문 트리거**: "여러 사람이 편집"한다고 하면 → 공동 편집이 되는 문서 형식을 우선 제안

**문서·자료의 선제 질문 항목** (사용자가 언급하지 않아도 성격에 따라 묻습니다. 2단계에서는 영향이 큰 항목만 선택합니다)
- 기준 시점: 현황·수치가 언제 기준이어야 하는가?
- 결론 위치: 결론을 앞에 둘지, 논거를 쌍은 뒤에 둘지
- 분량 상한과 우선순위: 줄여야 한다면 무엇을 먼저 빼지
- 후속 활용: 같은 내용을 다른 형식(요약본, 슬라이드)으로도 쓸지

### 4-3. Claude가 주도적으로 파고드는 항목 (웹앱·도구)

사용자가 언급하지 않아도, 해당 앱 성격에 따라 아래를 선제적으로 질문합니다. 2단계에서는 영향이 큰 항목만 선택합니다:

- **실시간성**: 입력할 때마다 즉시 처리할 것인가, 버튼 클릭 시 처리할 것인가?
- **실행 취소(Undo)**: 이전 상태로 돌아가는 기능이 필요한가?
- **복사/공유**: 결과물을 쉽게 복사하거나 공유할 방법이 필요한가?
- **키보드 단축키**: 자주 쓰는 동작을 단축키로 처리할 필요가 있는가?
- **처리 중 피드백**: 처리에 시간이 걸릴 경우 로딩 인디케이터가 필요한가?
- **모바일 대응**: 작은 화면에서도 동작해야 하는가?

### 4-4. 인터뷰 종료 조건

다음 중 하나에 해당하면 인터뷰를 마칩니다:

- 5개 영역이 모두 파악된 경우
- 사용자가 "그냥 만들어줘" 등으로 진행을 명시하는 경우 → 미확정 항목은 합리적 기본값으로 처리하고, 요약에 명시
- 총 인터뷰 라운드가 4회를 초과한 경우 → 남은 미확정 항목을 명시하고 종료

## 5. 요구사항 요약 출력

- 2단계: 질문 답변과 가정한 기본값을 2~3줄로 짧게 밝힌 뒤 바로 제작합니다.
- 3단계: 인터뷰 완료 후 아래 항목으로 요약을 채팅창에 출력합니다. 파일은 만들지 않습니다.

요약은 코드 블록 없이 일반 마크다운(소제목과 목록)으로 작성하고, 이모지는 사용하지 않습니다.

요약 항목
- 목표: 한 문장
- 갖춰야 할 것 (Must Have)
- 있으면 좋은 것 (Nice to Have)
- 피해야 할 것 / 제약 조건
- 미확정 항목: 항목별로 적용할 기본값과 함께 표기

## 6. 제작 진행

요약을 출력한 뒤 사용자 선택을 기다리지 않고 곧바로 제작을 시작합니다. 수정이 필요하면 후속 턴에서 반영합니다.

- 요구사항 문서(.md)는 사용자가 요청할 때만 만들고, 파일로 전달합니다. 저장 경로를 고정해 가정하지 않습니다.
- 제작 중 요약과 어긋나는 판단이 필요하거나 되돌리기 어려운 결정이 생기면 그 지점에서만 사용자에게 확인합니다.

---

## 7. 제작 시 요약 활용 방법

인터뷰 결과 요약은 제작 과정 전반에 걸쳐 다음과 같이 활용됩니다:

- **Must Have** 항목은 반드시 구현합니다. 기술적으로 불가능한 경우 사용자에게 먼저 알립니다.
- **Nice to Have** 항목은 복잡도가 낮은 경우 포함하고, 높은 경우 제외 후 사용자에게 고지합니다.
- **피해야 할 것** 항목은 코드 작성 중 체크리스트로 활용합니다.
- **미확정 항목**의 기본값은 결과물의 주석이나 README에 명시합니다.
- 웹앱·도구: 결과물은 실행 가능한 아티팩트로 만들어 채팅에서 바로 확인할 수 있게 합니다.
- 문서·자료: 산출 형식에 맞는 전용 스킬이나 도구로 제작하고, Must Have를 구성과 내용에 반영합니다. 미확정 기본값은 문서 첫머리에 한 줄로 명시합니다.
- 문서·자료: 최신 수치나 현황은 제작 전에 검색으로 확인하고 출처를 남깁니다.
- 기존 소스코드·아티팩트·문서를 바탕으로 새 앱이나 문서를 만들 때는 내용을 다시 써서 옮기지(전사) 않고, 파일을 복사한 뒤 필요한 부분만 수정합니다.
- 산출물(앱 화면 문구, README, 문서, 슬라이드)에는 이모지를 사용하지 않습니다.

## 8. 주의 사항

- 인터뷰는 도움이 되어야지, 부담이 되어서는 안 됩니다. 사용자가 짧게 답하면 그 답을 존중하고 다음으로 넘어갑니다.
- 이미 답변한 같은 항목을 두 번 이상 반복해서 묻지 않습니다.
- 질문은 개방형과 선택형을 적절히 섞되, 선택형은 질문 도구를 사용합니다(기타 입력은 도구가 기본 제공).
- 명확한 요청에는 질문하지 않습니다. 질문은 답에 따라 결과물이 달라질 때만 합니다.
- 이 스킬은 산출물의 품질 향상이 목적입니다. 인터뷰 자체가 목적이 아님을 항상 인식합니다.

# 사람이 읽을 수 있는 문서 개정

에이전트 문서는 쓰는 쪽의 작업 기록이다. 독자가 필요한 것은 결론·현재 상태·자기 할 일이다.
이 스킬은 기록을 독자용 문서로 바꾼다. 내용(사실·결정·위험)은 지키고 표현과 구조만 바꾼다.

## 1. 독자 모델

- 이 문서를 처음 읽는다. 이전 대화·다른 문서·작성자의 약속어를 모른다.
- 한 번에 붙잡을 수 있는 항목은 4개 안팎이다. 읽다가 앞 문단으로 돌아가야 하면 실패다.
- 첫 화면(약 10줄)만 읽고도 "무엇을 하는 문서인가, 지금 어디까지 왔나, 나는 무엇을 해야 하나"를 답할 수 있어야 한다.

## 2. 절차

0. **원문 형식 확인** — 원문이 `.html`·`.htm`·`.docx` 이면 먼저 마크다운으로 바꾼다. 표가 많은 문서이므로 pandoc 의 `-t gfm` 을 쓰며, 아래 명령이 이를 처리한다.

   ```bash
   bash ~/.claude/skills/human-readable-docs/scripts/to-md.sh <원문파일> [출력.md] [--force]
   ```

   - 출력 경로를 생략하면 원문 옆에 같은 이름의 `.md` 를 만든다. 이미 있으면 `--force` 없이는 덮어쓰지 않는다.
   - 병합 셀이 있는 표는 gfm 이 HTML 표로 남긴다. 스크립트가 개수를 알려 주면 해당 표를 직접 확인하고, 표의 행·열이 어긋났는지 원문과 대조한다.
   - 변환본은 사실 추출과 7절 원문 대조의 기준으로 쓴다. 변환 과정에서 머리글·각주·이미지가 빠졌는지 훑어본다. 이미지는 변환되지 않으므로 이미지에 담긴 사실은 따로 확인한다.
   - pandoc 이 없으면 스크립트가 직접 설치한다. scoop 이 없으면 PowerShell(Windows 에 있다고 가정한다)로 scoop 을 먼저 설치하고, `scoop install pandoc` 으로 pandoc 을 설치한다. scoop 은 관리자 권한 셸에서 설치가 거부되므로 일반 권한으로 실행한다.
   - scoop 경로는 SessionStart 훅 `~/.claude/hooks/session-env.sh` 가 `$SCOOP` → `~/scoop` → `/d/scoop` → `/c/scoop` 순으로 찾아 PATH 에 넣는다(이미 적용되어 있어 훅은 고치지 않는다). 설치 직후처럼 훅이 아직 돌지 않은 셸에서는 스크립트가 `~/scoop/shims` 를 PATH 앞에 붙인다. 스크립트 밖에서 pandoc 이나 scoop 을 직접 부를 때 PATH 에 없으면 `export PATH="$HOME/scoop/shims:$PATH"` 를 명령 앞에 붙여 실행한다.
   - 설치에도 pandoc 이 없으면 종료 코드 3 으로 알린다. 그때는 원문을 직접 읽고 사용자에게 변환을 못 했다고 보고한다.
1. **사실 추출** — 원문을 읽고 다음 다섯 종류로 나눠 적는다: 결정된 것 / 확인된 사실 / 미정인 것 / 해야 할 일 / 위험·제약.
2. **버릴 것 분류** — 4절의 금지 항목에 해당하는 문장을 표시한다. 지우기 전에 그 문장이 위 다섯 종류 중 하나를 담고 있는지 본다. 담고 있으면 문장만 고쳐 살린다.
3. **재구성** — 3절의 절 구조에 맞춰 새로 쓴다. 원문 순서를 따르지 않는다. 덧붙임 절(§10, §11…)은 본문에 녹여 하나의 최신 상태로 만든다.
4. **문장 다듬기** — 5절 규칙으로 문장을 고친다.
5. **원문 대조** — 완성한 개정본을 원문과 항목별로 맞춰 본다. 누락된 사실과 원문에 없는 추가·단정을 찾아 고친다. 기준은 7절이다.
6. **점검** — 8절 점검표를 통과시킨다.
7. **저장·보고** — 원본을 덮어쓰지 않는다. 사용자가 지정한 위치가 없으면 원본 옆에 `<이름>.읽기용.md` 로 저장한다. 보고에는 삭제·통합한 범주, 뜻을 알 수 없어 일반화한 코드, 의미가 달라질 수 있어 확인이 필요한 곳을 쓴다.

## 3. 문서 구조

위에서 아래로 "큰 그림 → 세부"의 순서로 쓴다. 문서 성격에 맞는 절만 쓰고 이름은 고정이 아니다. 같은 절이 두 번 나오지 않게 한다.

| 절 | 담는 것 | 길이 |
|---|---|---|
| 요약 | 결론 1문장, 현재 상태, 독자가 해야 할 일·결정할 일 | 3~5줄 |
| 배경 | 왜 이 일을 하는가. 요구가 나온 계기와 해결할 문제 | 1~2문단 |
| 개요 | 무엇을 만드는가. 완성되면 사용자가 보게 되는 모습 | 1~2문단 |
| 범위 | 포함하는 것과 포함하지 않는 것. 제외 항목은 이유를 한 구절로 | 두 목록 |
| 방침 | 접근 방법, 데이터·구조 구성 전략, 핵심 선택과 그 이유 | 항목당 2~3문장 |
| 작업 | 순서대로 할 일. 각 작업은 "누가 / 무엇을 / 끝났다는 기준" | 표 또는 번호 목록 |
| 미정 사항 | 아직 정해지지 않은 것, 정할 사람, 정할 시점 | 목록 |

- 유보·미확인·가정은 흩뿌리지 말고 **미정 사항** 한 곳에 모은다. 본문은 확정된 것만 단정형으로 쓴다.
- 근거·출처·변경 이력은 문서 끝 짧은 절로 내린다. 본문 흐름을 끊지 않는다.

## 4. 금지

### 4.1 항목 번호로 다른 곳을 가리키기

`D1`, `AM1`, `L01`, `T07`, `A08`, `W-ST03`, `§10.3`, "위 7절 참조" 같은 지칭을 쓰지 않는다. 독자는 번호의 뜻을 기억하지 못한다.

- 다른 곳의 내용이 필요하면 그 내용을 한 구절로 다시 쓴다.
  - ✗ `L05는 L04와 L03 이후에 한다.`
  - ✓ `거래처 화면의 권한 연결은 직원 인증 연동이 끝난 뒤에 한다.`
- 표 행에 번호 열을 두지 않는다. 행은 이름으로 구별한다. 번호가 외부 시스템의 정식 식별자(이슈 번호, 파일명)이면 그대로 쓰되 처음 나올 때 뜻을 함께 쓴다.
- 문서 안 링크가 꼭 필요하면 절 제목을 그대로 쓴다(예: 「미정 사항」 참고).

### 4.2 문서 자기 서술

- "이 문서는 ~이다", "이번 계획은 ~가 아니다", "본 절은 ~를 보완한다" 같은 문서 자신에 대한 설명을 쓰지 않는다.
- 문서의 검토·수락·보완 이력("Planner 수락", "2차 보완본", "계속 하자 요청 반영")을 본문에 쓰지 않는다. 필요하면 맨 끝 이력 한 줄로 둔다.
- 하지 않는 일의 나열("A를 확정하지 않는다. B를 승인하지 않는다. C가 아니다…")을 쓰지 않는다. 오해가 실제로 생길 것 한두 개만 범위의 "제외"에 쓴다.
- "확정이 아니다", "추정이다", "단정하지 않는다"를 문장마다 붙이지 않는다. 확인되지 않은 것은 미정 사항에 한 번만 쓴다.

### 4.3 기타

- 같은 내용의 반복(요약·본문·결론에서 되풀이)을 쓰지 않는다. 한 사실은 한 곳에만 둔다.
- 작성 과정 서술("직접 대조했다", "재실행하지 않았다")은 독자의 판단에 영향을 줄 때만 한 줄로 남긴다.
- 역할·책임 소재를 가리는 수식("예정", "검토 대상", "경계")으로 담당자·기한을 흐리지 않는다. 모르면 "미정"이라고 쓴다.
- 새 사실·수치·일정을 만들어 넣지 않는다.

## 5. 문장 규칙 (ASD-STE100 차용)

1. **한 문장에 한 가지 정보.** 문장이 60자를 넘거나 쉼표·"~하며"로 이어지면 나눈다.
2. **능동·현재형, 평서체 "~한다".** 주어를 숨기는 피동("확인되어야 한다")을 "누가 확인한다"로 바꾼다.
3. **용어 고정.** 한 개념에 한 단어만 쓴다. "직원/사용자/계정", "화면/페이지/UI"를 번갈아 쓰지 않는다. 첫 등장에서 정의하고 끝까지 같은 말을 쓴다.
4. **약어·영문 식별자는 첫 등장에 풀이**하고, 독자에게 필요 없으면 쓰지 않는다.
5. **조건은 앞에, 결과는 뒤에.** "~이면 ~한다." 조건이 둘 이상이면 목록으로 쓴다.
6. **절차는 한 단계에 한 동작.** 순서가 있으면 번호 목록, 없으면 글머리 목록을 쓴다.
7. **명사 나열을 동사로 푼다.** ✗ "인증·세션·인가 연동 검증 수행" → ✓ "로그인 후 세션이 올바른 권한으로 만들어지는지 확인한다."
8. **괄호·슬래시 삽입을 줄인다.** 괄호 안에 문장을 넣지 않는다. "A/B/C"로 뭉친 것은 목록으로 푼다.
9. **지시어("이것", "해당", "상기")를 줄이고** 대상을 다시 쓴다.
10. **추상어를 구체어로.** "적절히", "필요 시", "관련 사항" 대신 조건과 대상을 쓴다.

## 6. 밀도 규칙

- 표는 열 3개 이하, 셀은 한 구절이다. 셀에 문단이 들어가면 표를 목록이나 소절로 바꾼다.
- 목록은 항목 7개 이하다. 넘으면 묶음에 이름을 붙여 나눈다.
- 한 절은 한 화면 안에 들어가는 분량을 목표로 한다. 길어지면 소절로 나누고 소절 제목은 내용을 말하는 문장형 명사구로 쓴다("거래처 화면은 로그인 후에만 열린다").
- 강조는 결정 사항·위험에만 쓴다. 굵은 글씨가 문단마다 있으면 강조가 없는 것과 같다.

## 7. 보존 규칙 — 줄이다가 사실을 잃지 않는다

읽기 쉽게 줄이는 일과 사실을 지우는 일은 다르다. 다음 다섯 가지는 줄이는 과정에서 가장 자주 사라진다.

1. **검증 수준과 수락 범위를 남긴다.** "직접 확인한 것 / 보고받은 값 / 확인하지 않은 것"의 구분, 무엇을 수락했고 무엇을 수락하지 않았는지, 실행하지 않은 시험, 합산하면 안 되는 수치를 한 곳(「현재 상태」)에 모은다. 독자가 "어디까지 믿어도 되는가"를 알 수 있어야 한다. 수치만 남기고 "무엇을 실행한 결과인지, 무엇의 증거가 아닌지"를 지우지 않는다.
2. **인계 지시는 사실이다.** 다른 사람이 받아서 할 일의 순서, 적용 방법(예: 어느 패치를 어느 패치에 덧붙이지 않는다), 반환·보고 기준, 다른 작업과의 충돌·중복 방지 조건은 삭제하지 않고 「작업」에 옮긴다.
3. **미정을 확정으로 바꾸지 않는다.** 원문이 "정한다", "제안한다", "확인 후 확정한다"로 쓴 것을 "~한다"는 단정으로 쓰지 않는다. 요약이 본문보다 강하게 말하지 않는다("명세가 끝났다"는 원문이 기본안까지만 제공했다면 쓰지 않는다). 결정 권한과 담당도 원문의 범위를 넘겨 넓히지 않는다. 확신이 없으면 원문 표현을 그대로 둔다.
4. **번호를 없앨 때 가리키던 대상을 다시 쓴다.** 번호가 가리키던 내용을 한 구절로 풀어 쓴다. 뜻을 알 수 없는 코드는 임의로 풀거나 지우지 말고 일반화한 표현으로 바꾼 뒤, 보고에 "확인 필요"로 적는다. 원문 번호가 외부 문서의 식별자라면 뜻을 붙여 유지한다.
5. **원문에 없는 것을 더하지 않는다.** 새 결정, 새 수치, 새 담당, 새 일정, 추정한 상태를 넣지 않는다. 문장을 연결하다가 생기는 인과("~이므로")도 원문에 근거가 있는 것만 쓴다.

개정이 끝나면 원문 대조(절차 5단계)로 이 다섯 가지를 확인한다. 원문의 절 하나하나가 개정본 어디로 갔는지 대응표를 만들고, 대응이 없는 항목은 삭제로 둘지 되살릴지 판단한다. 삭제해도 되는 것은 4.2·4.3의 자기 서술과 반복뿐이다.

## 8. 점검표

- [ ] 첫 10줄만 읽고 목적·현재 상태·할 일을 말할 수 있다.
- [ ] 검증 수준(직접 확인 / 보고값 / 미확인)과 수락·미수락 범위가 한 곳에 남아 있다.
- [ ] 인계 지시(적용 순서·반환 기준·중복 방지)가 「작업」에 있다.
- [ ] 원문의 미정·제안이 확정 문장으로 바뀌지 않았다. 요약이 본문보다 강하지 않다.
- [ ] 없앤 번호가 가리키던 내용이 본문에 있다. 뜻을 모르는 코드는 보고에 "확인 필요"로 표시했다.
- [ ] 원문 대조표에서 대응이 없는 항목이 모두 의도한 삭제다.
- [ ] 항목 번호(`D1`, `L01`, `§3` 등) 지칭이 없다. 외부 식별자는 뜻이 함께 있다.
- [ ] "이 문서는", 검토·수락 이력, 부정 나열이 본문에 없다.
- [ ] 미정·가정이 미정 사항 한 곳에만 있다. 본문은 확정 사실만 말한다.
- [ ] 같은 사실이 두 곳에 있지 않다.
- [ ] 한 개념에 용어가 하나다.
- [ ] 60자를 넘는 문장이 없다.
- [ ] 원문의 결정·수치·날짜·이름·경로·위험이 그대로 남았다. 새 사실이 없다.
- [ ] 각 작업에 담당·완료 기준이 있거나 "미정"으로 표시돼 있다.

## 9. 고쳐 쓰기 예

**원문**
> L04는 L01과 L03 이후이며 계정 저장소 공유·SSO는 전제하지 않는다. 기존 A08 기술자료를 재사용해 차이만 확인하고, 계획 문서 작성은 배포 승인이 아니다. 실제 직원·유효 고객 소속을 서버에서 검증하고 SCM 컨텍스트를 구성하되 발급·갱신·만료·로그아웃·실패를 실제 계약과 연결한다.

**개정**
> **직원 인증 연동** (담당: 개발자)
> 선행 작업: 현재 인증 방식 조사, 로그인 화면 구현.
> 할 일: 로그인한 직원이 활성 고객사 소속인지 서버에서 확인하고, 그 결과로 SCM 세션을 만든다. 세션의 발급·갱신·만료·로그아웃도 같은 방식으로 처리한다.
> 완료 기준: 소속이 없는 직원은 로그인할 수 없고, 소속이 있는 직원은 자기 고객사의 화면만 본다.
> 제외: 다른 시스템과의 계정 공유와 통합 로그인(SSO)은 이번 작업에서 다루지 않는다.

변경 요점: 번호 지칭 → 내용 서술, 문서 이력 문장 삭제, 완료 기준 명시, 부정 나열 → 제외 한 줄.

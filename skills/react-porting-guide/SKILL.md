# React 포팅 사전 가이드 작성 스킬

## 목적

레거시 ASP.NET MVC + jQuery + SlickGrid 기반 페이지를 React로 포팅하기 전에,
기존 페이지의 **모든 기능·로직·조건부 UI·외부 의존성**을 빠짐없이 점검·문서화한다.

산출물은 다음 두 곳에 동일 내용으로 저장된다:

1. 프로젝트: `{프로젝트루트}/.docs/react-porting/{page-slug}.md`
2. 계획 보관: `C:/Users/sooop/.claude/plans/{page-slug}-guide.md`

---

## 워크플로우

```
인자 파싱 → Phase 1: 파일 탐색 → Phase 2: 심층 인터뷰 → Phase 3: 가이드 작성 → 검증
```

## Phase 0: 인자 파싱

`$ARGUMENTS`에서 페이지 경로 힌트를 읽는다.

- 예시: `Settle/Compensation` → 컨트롤러 영역 `Settle`, 페이지명 `Compensation`
- 힌트가 없으면 사용자에게 페이지 경로를 먼저 물어본다.

`page-slug`는 인자를 kebab-case로 변환하여 사용할 수 있으나, 레거시 페이지의 라우트가 현대적인 라우트 컨벤션을 따르지 않을 수 있으므로
검토하여 더 나은 버전을 추천한다. 

예: `Settle/Compensation` → `settle-compensation` -> `billing/compensations`

## Phase 1: 파일 탐색 (Explore 에이전트 사용)

**반드시 Explore 서브에이전트를 사용**하여 다음 파일들을 병렬 탐색한다.

### 탐색 대상 파일 패턴

| 파일 역할 | 경로 패턴 |
|-----------|-----------|
| 뷰 (Razor) | `QX.Store.Web/Views/{Area}/{Page}.cshtml` |
| 페이지 스크립트 | `QX.Store.Web/Content/PageScripts/{Area}/{Page}.js` |
| 컨트롤러 | `QX.Store.Web/Controllers/{Area}Controller.cs` |
| 다이나믹 데이터 설정 | `QX.Store.Web/Config/DynamicData/{Area}.config` |
| 다국어(ko) | `QX.Store.Web/MultiLang/ko/{Area}/{Page}.lang` |

파일을 찾을 때는 `fd -i "{Page}" {프로젝트루트} -t f` 로 먼저 위치를 확인한다.

### Explore 에이전트에게 지시할 탐색 항목 (빠짐없이)

1. **페이지 진입 및 초기 상태** — 액션 파라미터, ViewBag 기본값, JS 부트스트랩 시퀀스
2. **검색/조회 폼** — 입력 필드 전체, 검색 조건, 기간 제한, 키워드 변환 규칙, 호출 엔드포인트, SP 파라미터 매핑
3. **데이터 바인딩 / 그리드** — 컬럼 정의, 포매터, 에디터, 그리드 옵션, 행 클릭 동작, 상세 영역 바인딩, 페이지네이션
4. **모든 제출(Submit) 케이스** — 트리거, 페이로드, 클라이언트 검증, 서버 로직, 성공/실패 처리
5. **레이어/팝업/모달** — 트리거 조건, 표시 내용, 동작 (인라인 영역, 별도 창, 알림 포함)
6. **조건부 UI / 권한 / 상태 제어** — 상태값에 따른 컨트롤 활성/비활성, 사용자 권한 주입
7. **외부 의존성** — jQuery 플러그인, 공용 유틸(`UIUtil.*`, `SlickGridFactory`, `NumberUtil.*`, `RST`), 다이나믹 데이터 추상화
8. **잠재 결함 / 데드코드** — 미존재 DOM 참조, 미사용 함수·분기, 명칭 오기재, 데이터 미바인딩 항목

각 항목에 대해 **파일경로:라인번호** 형식으로 참조를 제공받는다.

## Phase 2: 포팅 가이드 지침

1. 가이드는 React 포팅 개발자용 구현 사양서이면서 비즈니스 로직 이해용 도메인 명세를 모두 포함합니다. 
2. 화면, 상태, 엔드포인트, 검증 규칙과 상태의 의미, 플로우까지 망라해야 함
3. 레거시 구현에서 발견된 결함이나 데드코드는 권고대로 정정된 사양으로 작성합니다.
4. 주요 코드 스니펫은 '파일:라인'으로 인용하여 캡쳐한다. 
5. 상태 전이/플로우 다이어그램 포함(Mermaid)
6. 엔드포인트, SP 파라미터 표
7. DOM ID <-> React 상태 매핑표


### UI 및 레이아웃 설계

- 레거시 구현은 데이터그리드를 상단에 두고 하단에 상세 폼을 한 페이지로 결합한 구조가 많다. **이 구조를 그대로 따라서는 절대 안된다** 
- 데이터 그리드를 페이지의 베이스로 하고 모든 폼은 모달로 띄운다.
- 폼 상세가 탭으로 분리된 경우, 각 탭이 독립적인 비즈니스 성격인지를 판단하여 개별 모달로 분리할 지, 하나의 모달 다이얼로그 내 탭이 존재할지를 판단한다. 
- 이러한 판단은 사용자에게 심층 인터뷰를 통해 확인해야 한다. 
- 화면 구조 및 디자인은 리액트 프로젝트 내 다른 주요 페이지를 몇 개 참고하고, 결정 방향에 대해서는 사용자에게 심층 인터뷰를 요청한다.
- UI의 디테일은 프로젝트 UI 관련 규칙 및 UI 감사 스킬(이 스킬은 tx-front-react의 경우 .cursor/skills에 있다)을 참고하고, 참고할 페이지에서 구현한 부분은 대부분 포함시킨다.

### 서버 액션 

- 서버 액션이 RMS 컨트롤러를 호출하고 있다면, 해당 코드를 끝까지 추적한다. 만약 최종적으로는 SP 호출을 중계하고 있다면 서버 액션은 SP 호출로 포팅한다.
- 로직이 복잡한 경우 자체 서버 액션으로 구현할 수 있는 복잡도인지 검토한다. 
- 기존 컨트롤러가 지나치게 복잡하거나 비대한 경우, 또는 외부 의존성을 갖는 경우, 기존 컨트롤러를 호출한다.

## Phase 3: 가이드 작성

인터뷰 결과와 탐색 내용을 종합하여 가이드를 작성한다.



### 가이드 문서 구조 (표준 목차)

```markdown
# {PageName} 페이지 React 포팅 가이드

## 1. 개요
   1.1 페이지 목적 / 사용자
   1.2 화면 구성 한눈에 보기 (ASCII 와이어프레임)

## 2. 도메인 배경
   - 상태 코드 체계 (코드·표시명·의미·제어 가능 여부 표)
   - 기타 도메인 코드 (사유, 유형 등)

## 3. 페이지 진입 및 초기 상태
   - 라우팅/액션 파라미터
   - ViewBag/서버 초기값
   - JS 부트스트랩 시퀀스 (트리 형식)

## 4. 검색/조회
   - 폼 필드 일람 표
   - 키워드 변환 규칙
   - 호출 엔드포인트 및 SP 파라미터 표
   - 응답 포맷
   - 자동 조회 트리거 일람

## 5. 데이터 바인딩 / 그리드
   - 컬럼 정의 표 (필드·표시명·포매터·에디터)
   - 그리드 옵션 표
   - 행 클릭 → 상세 영역 바인딩 매핑 표
   - 페이지네이션 동작
   - **React 구현 시 인계**: 이 페이지에 그리드/목록이 있으면, 실제 React 구현 단계에서는 레거시 그리드(SlickGrid 등) 마크업·옵션을 그대로 옮기지 말고 프로젝트의 데이터 그리드 정책·공통 그리드 컴포넌트(TanStack Table 기반 헤더/푸터/전역필터/정렬 등 공통 모듈)를 먼저 확인한다. 프로젝트에 그리드 전용 스킬(예: `data-grid`)이 있으면 **이 가이드 작성 직후 그 스킬을 연다** — 조사 문서 작성으로 끝내지 않는다.

## 6. 제출(Submit) 케이스
   - [SUBMIT-N] 각 케이스: 트리거/메서드/URL/페이로드/클라이언트검증/서버처리/성공-실패처리
   - [NAV] 페이지 이동/새 창 케이스

## 7. 레이어/팝업/모달
   - 인라인 영역 (트리거·내용·동작)
   - 별도 창 / 외부 페이지
   - 시스템 알림 / 인디케이터

## 8. 조건부 UI / 권한 / 상태 제어
   - 상태 매트릭스 표 (조건·컨트롤 활성여부·의미)
   - 사용자 권한 처리

## 9. 외부 의존성 / 공용 컴포넌트
   - 표: 컴포넌트·역할·React 포팅 시 대응 방향
   - `SlickGridFactory`/그리드 플러그인 행의 "React 포팅 시 대응 방향"에는 반드시 **"프로젝트의 그리드 정책/공통 컴포넌트(전용 스킬이 있으면 해당 스킬)를 따른다"**를 명시하고, 임의의 신규 그리드 구현을 제안하지 않는다

## 10. 핵심 함수/상태 변수 색인
    - 전역 모듈 변수 표
    - 핵심 함수 요약 표

## 11. DOM ID ↔ React 상태 매핑 표

## 12. 사용자 액션 플로우 다이어그램 (Mermaid sequence)

## 13. 보상/상태 전이 다이어그램 (Mermaid stateDiagram) — 해당 시

## 14. 다국어 키 인덱스 표

## 부록 A — 주요 코드 스니펫 (파일:라인 인용)
    - 검색 ajax 블록
    - 각 Submit 케이스 ajax 블록
    - 그리드 컬럼 정의
    - 행 클릭 핸들러
    - 컨트롤러 액션
    - DynamicData config 항목

## 부록 B — React 포팅 시 정정 권고 (인터뷰 결과에 따라 포함/제외)
    - 각 결함 항목: 현행·권고 형식으로 기술
```

### 가이드 작성 규칙

- 모든 코드 인용은 `파일경로:라인번호` 캡션 포함.
- Mermaid 다이어그램은 `sequence` (플로우)와 `stateDiagram-v2` (상태 전이) 사용.
- 표는 GitHub Flavored Markdown 표 형식.
- 금액 포맷·날짜 포맷 등 포매터 로직은 정확히 캡처.
- "현행 동작"과 "권고"를 절대 혼용하지 않음 — 인터뷰 결과에 따라 명확히 분리.

## Phase 4: 파일 저장 및 검증

### 저장 절차

```
1. 프로젝트 .docs/react-porting/ 폴더 존재 확인 (없으면 New-Item -ItemType Directory -Force)
2. 가이드 본문 Write → .docs/react-porting/{page-slug}.md
3. copy 명령으로 C:/Users/sooop/.claude/plans/{page-slug}-guide.md 에 복사
   (CLAUDE.md 규칙: 파일 복사는 cp/copy 사용, Read/Write로 복사 금지)
4. fd 로 두 경로에 파일이 존재함을 검증
```

### 자체 검증 (작성 후)

아래 5개 시나리오를 확인하고 결과를 사용자에게 보고한다:

| 시나리오 | 확인 방법 |
|----------|-----------|
| a) 모든 ajax URL이 §6 제출 케이스에 등장하는가 | `rg` 로 `.js` 파일의 `url:` 라인 추출 후 대조 |
| b) SP 파라미터 표가 `.config` 파일과 일치하는가 | 3개 랜덤 파라미터를 `.config`에서 grep 확인 |
| c) 행 클릭 바인딩 매핑 표가 `.js` onClick 핸들러와 일치하는가 | 매핑 표 DOM ID를 소스에서 grep |
| d) 상태 매트릭스의 모든 코드가 도메인 배경 §2에 정의되어 있는가 | 목측 확인 |
| e) 파일:라인 인용 3건을 무작위 선택하여 실제 소스와 대조 | `rg -n` 확인 |

검증 통과 후 사용자에게 결과 파일 경로를 안내한다.

### 다음 단계 (구현 인계)

**구현 시 일반 수준의 모델(sonnet, normal effort)의 서브 에이전트를 전개(fan out)하여 구현하고, 높은 수준의 모델이 이 작업을 오케스트레이션한다.** 작업 중 낮은 수준의 모델이 오케스트레이션 업무를 이어가지 않아야 한다.

**리액트 프로젝트 내에서 참고할 포팅 선례가 되는 페이지를 찾고, 사용자에게 보고한 후 참조 구현으로 설정한다**

## 주의 사항

- **파일 탐색에는 반드시 Explore 서브에이전트 사용** — 대형 파일(컨트롤러 등)은 해당 페이지 관련 섹션만 스캔.
- **파일 이동·복사는 `cp`/`copy`/`xcopy` 사용** (CLAUDE.md 규칙). Read/Write로 복사하지 말 것.
- **파일 탐색은 `fd`**, **내용 검색은 `rg`** 사용.
- 가이드 작성 중 코드 스니펫의 라인 번호는 실제 소스와 반드시 일치해야 한다. 추측하지 말고 Read 도구로 확인.
- 레이아웃·팝업·모달을 조사할 때 "레이어 아닌 것"도 명시 (예: "인라인 영역, 모달 아님").
- 데드코드·잠재 결함은 본문에 섞지 않고 부록 B에만 기술.
